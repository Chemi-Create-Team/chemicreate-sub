# 第4段階準備：現在の蒸気タービン仕様と改修上の論点

基準：work `cb0ec88`。GitHub workと一致を確認。現行コードの静的調査であり、今回は本体改修・ゲーム内再試験を行っていない。本資料は「現在の仕様」と「今後決める仕様」を区別する。

## 1. 現状の結論

現行タービンはCreate回転動力を生成する高圧・低圧の複合設備である。主な出力はRPMと応力容量SUであり、SteamTurbineBlockEntityにFE発電量の計算はない。

**第1〜第3段階の水・蒸気の総質量・総エネルギー基準へ移行済みではない。** 蒸気の整数mBだけを保存し、その流量から速度・SUを決める。入口の温度・圧力・比エンタルピー差から仕事を算出しない。第4段階は見た目だけでなく、この計算・搬送・保存境界を改修する必要がある。

## 3. 構造と成立条件

タービンは軸を持ち、その周囲へ羽根・ケーシングと両端部を取り付ける。BlockStateには `blades=1..6`、`size_1/2/3=1..7`、`casing` がある。ただし実際の設置上限は登録時のコンストラクターと高圧・低圧別の構造判定に制約される。プロパティの最大値が全形式で使えるという意味ではない。

### 個別の構造判定

| 条件 | 高圧側 | 低圧側 |
| --- | --- | --- |
| 判定対象の軸長 | 1〜3 | 5で固定 |
| 羽根数の成立閾値 | 18以上 | 8以上 |
| ケーシング | 全軸位置で完成していること | 全軸位置で完成していること |
| 端部 | 両端、2個 | 両端、2個 |
| ケーシングの判定半径 | 1 | 2 |

これはコードのカウント値であり、画面上の羽根1枚とアイテム1個の対応を無条件に同一視しないこと。高圧で軸長1でも単純に完成できるとは限らず、羽根閾値などの全条件を満たす必要がある。

### 複合設備

高圧側・低圧側の両方を成立させ、同軸方向の接続シャフト1〜5個でつなぐ。さらに、高圧側と低圧側を結ぶ別の排気配管が必要。機械的につながっているだけでは運転成立にならない。

`getGeneratedSpeed()` と `isSteamOperational()` は施設の `operational()` に依存する。単独の高圧タービンを置けば通常運転できる設計ではない。

## 4. 蒸気入力・保存・排気

流体IDは既存の `create_heavy_indusstry:steam`。SteamHandlerは2つの論理タンクを公開する。

| 論理タンク | 内容 |
| --- | --- |
| 0 | 入力蒸気の整数mB。容量は各タービンへ割り振った最大消費量の2倍 |
| 1 | 回収可能な排気の整数mB。容量64000 mB |

- 通常の流体fillは、運転成立した高圧側でのみ受け付ける。低圧側は内部の `fillExhaustSteam(int)` で供給される。
- 通常のdrainは低圧側の排気バッファからのみ可能。
- 本体登録のCapabilityプロバイダーはside別に異なるハンドラーを選ばず、同じハンドラーを返す。周辺部品経由の接続については各中継処理を別途確認する必要がある。
- SIMULATEは量を問い合わせ、EXECUTEで整数バッファを変更する。
- **入力FluidStackのData Componentsは保持しない。** fillで量だけを取り込み、取り出しでは `new FluidStack(STEAM, amount)` を新規作成する。温度・SPECIFIC_ENERGY・他MODの追加データを引き継ぐ処理はない。
- したがって第3段階の過熱蒸気を流体IDとして受け付けても、その熱的状態に応じた運転をしているわけではない。

## 5. 現行の消費量・回転・SU計算

`TurbineFacility` の定数：

| 項目 | 値 |
| --- | --- |
| 最大ボイラー換算数 | 4 |
| 最大ボイラー1基の蒸気換算 | 6400 mB/t |
| 高圧側最大消費 | 25600 mB/t |
| 低圧側最大消費 | 12800 mB/t |
| 高圧→低圧の排気係数 | 0.5 |
| 最大合計応力容量 | 2359296 SU |
| 高圧側の割当 | 合計の70% |
| 低圧側の割当 | 合計の30% |
| 軸の生成速度上限 | 256 RPM |
| 基準ローター表示速度 | 2560 RPM |

施設の上限をタービン数で割り、余りはインデックス順に配る。各バッファからその上限まで毎tick消費する。バッファ容量は割当消費量の2tick分。

実際にCreateへ返す生成速度は、高圧側の入力集計から `min(256, 高圧入力 / 25600 × 256)`。

SUは高圧・低圧の流量比からそれぞれ線形に求める。低圧側の有効入力は、低圧実入力と高圧入力×0.5の小さい方。最大SUの70%・30%を各段の最大流量比で乗じて加算する。Createへの応力容量係数は合計SUを実生成RPMで割って返し、施設の容量担当だけが供給する。SUとSU/RPM相当の係数を混同しないこと。

局所のローター表示速度には `min(2560 × performance, 蒸気消費量 / 10)` を使い、局所出力表示はさらに1/10にする。成立時の `performanceMultiplier` は羽根充足率を1で打ち切るため、羽根を無制限に追加して熱効率が伸びる仕組みではない。

`TurbineAcceleration` には入力速度×10を目標とする追従状態があり、1200tickの定数から増減ステップを計算する。ただし全形式の発電出力が必ず60秒で定格へ達するという仕様ではない。該当する形式と表示・実出力の使い分けを改修時に整理すること。

## 6. 質量・エネルギー上の問題

1. 高圧消費量の50%だけを低圧へ転送する。気体の体積換算として作られた旧係数を、1000mB=1kgの新モデルへそのまま適用すると質量が減る。
2. 高圧消費は先に確定し、転送呼び出しの戻り値を消費量のロールバックに使用しない。低圧満杯・転送不能の場合も、全蒸気を保存しているとは言えない。
3. 低圧で消費した量を排気バッファへ加えるが、64000 mBを超える分は `min` で切り捨てる。コメント上は従来の大気放出を残した仕様で、閉塞で完全停止する方式ではない。
4. 膨張による温度低下、湿り度、入口／出口圧力比、エンタルピー差、機械効率から仕事を計算していない。生成SUに対応するエネルギーを蒸気Uから差し引く台帳がない。
5. 排気は温度・U情報を持たない新しい蒸気Stackになる。復水器で受けても、タービンでどれだけ仕事を取り出した蒸気なのか復元できない。
6. 新しい圧力・温度損傷をタービン内部の実状態から評価する専用の統合はない。周辺配管の損傷システムがあることと、内部容器の安全機構が完成していることは別。

これらは改修の必要箇所であり、今回修正したわけではない。既存仕様として意図された大気放出と、新サイクルの保存則をどう両立するかは新指示で確定する必要がある。

## 7. Createボイラー互換経路

`BoilerSteamOutput` はタービンへ専用探索・直接転送する旧経路。ボイラーの稼働・熱・給水を参照し、パイプ探索上限256、最大4基換算、最大蒸気25600 mB/tを用いる。

水1 mBから蒸気50 mBという `STEAM_PER_WATER_MB=50` が残る。新しい質量換算と一致せず、標準のFluidStack搬送へ単純に置換すれば同じ性能になるわけではない。通常のCreateボイラー互換性を維持する場合も、変換境界で質量・熱量をどう定義するかを明示する必要がある。

## 8. 保存・表示・サーバー処理

入力・排気の整数バッファ、消費量、局所生成速度、表示速度、端部状態、加速状態などをNBTに保存する。温度・総熱エネルギーの保存ではない。

サーバーtickでは蒸気消費、施設検索、排気転送、回転更新、SU再評価を行い、消費があるtick等に `sendData()` を呼ぶ。施設探索・構造集計・排気網探索が複数の計算箇所から呼ばれるため、新しいモジュールのような構造キャッシュを前提とした軽量化が必要か、プロファイルで確認する価値がある。現時点で負荷数値は測定していない。

クライアントではローターや蒸気パーティクルを表示する。ゴーグルの個別メソッドには詳細行を構築する箇所がある一方、現行の表示整理・Mixinもあるため、単一メソッドだけを見て画面全体の行数を断定しない。第4段階でも概要最大4行・詳細Display Linkの方針を維持する。

## 9. 第4段階のプロンプトで確定すべき項目

- 高圧・低圧の2段を必須にするか、単段でも運転し増設できるか。現在の固定低圧長5・羽根閾値等を維持するか。
- 出力をCreate回転動力にするか、FE発電機を別設備として接続するか。SU・RPMと物理仕事量の換算をどう定義するか。
- 入口温度・圧力・質量流量・出口背圧・効率から仕事を算出する近似。抽出した仕事と排気Uを同じ台帳で保存すること。
- 高圧→低圧で質量を減らさず、出口温度・U・湿り状態を渡す。段間再熱の有無。
- 復水器の真空が出力へどう影響するか。満杯・閉塞・冷却不足で流量を制限するか、大気排気モードを許可するか。
- 回転慣性・負荷・過速度・湿り蒸気・高温高圧の損傷をどこまで今回実装するか。
- 旧ボイラー互換を残す場合の50倍換算の廃止／変換方針。旧タービン登録を残すか置換するか。
- キャッシュ再計算、部品撤去、保存・再起動、SIMULATE、部分受入れの原子性と保存則。
- 第1〜第3段階の既存設備とAPIを再利用し、潜熱を二重計上しない。新規GUIを増やさず、組立→設定→負荷調整→復水器連携→異常対応のPonderを用意する。

## 10. 検証の位置づけ

今回は仕様資料作成のみで、ゲーム内動作・ベンチマークは再実施していない。既存テストにはModularPortsGameTests・PlantTutorialGameTestsなどからタービンを参照するものがあるが、質量・エネルギー保存型の膨張サイクルの検証が完成している根拠にはしない。

第4段階では入口／全段／排気／復水器の質量とエネルギー台帳、出力仕事、ゼロ流量、満杯、逆圧力差、濡れ蒸気、構造撤去、複数接続、再ロードを独立して検証する必要がある。
