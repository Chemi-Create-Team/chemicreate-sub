# 核融合炉・制御盤・蒸気タービン 長時間稼働試験

## 結論

25×25×17の核融合炉を制御盤から冷間始動し、80パーセント（核融合熱400 MW）で20,000 tick保持した。3組の高圧・低圧タービン、軸直結電動発電機、大型フライホイール、50 bar耐圧ドラムを含む閉ループは自己給電へ移行し、異常発熱・爆発・水や蒸気の消失なしで完走した。

報告されていた9件はすべて修正し、個別回帰試験と実プラント試験を追加した。冷間始動試験の定常点では、ブランケット250.81 °C、冷却水174,431 mB/t、ドラム20.10 bar、タービン軸115.95 MW、自己給電後の正味軸出力73.82 MWだった。後半区間の蓄熱は0.087 MWまで収束しており、暴走方向の温度上昇はない。

## 対象と実装

- 試験日：2026-11-07
- 対象：Minecraft 1.21.1 / NeoForge 21.1.219 / Create 6.0.10 / Java 21
- 実装コミット：`63a816a801fc84449998704d54b572df152f1dc6`
- 長時間試験：`./gradlew runFusionPlantGameTestServer`
- 生データ：`run/fusion-plant-result.json`

主な追加・変更は次のとおり。

- 炉の横に置く20 kV・最大120 MW・効率95パーセントの軸直結電動発電機を追加した。隣接する大型フライホイールが必須で、通常運転時は軸から42.105 MWを受けて炉へ40 MWを供給する。
- 大型フライホイールの伝達上限と回転中の蓄勢出力を修正し、炉の短い電源切替を吸収できるようにした。
- 50 bar対応の耐圧タンクを追加し、蒸気ドラムとして使用した。
- 炉冷却の設計上限を250 °Cとし、独立した温水5系統・冷水5系統で熱を搬送するようにした。
- 3組の高圧・低圧タービンには独立した蒸気供給管を使い、復水は各列の受槽へ落としてから1本の昇圧ポンプでドラムへ戻す。
- 電動発電機と耐圧タンクにはレシピ、モデル、テクスチャ、日英中の表示、Ponderを追加した。

## 試験プラント

| 部分 | 構成 |
| --- | --- |
| 核融合炉 | 25×25×17トカマク。D₂/T₂燃料、液体He超電導磁石、ブランケット、ダイバータを含む |
| 制御 | 3×2の原始的な制御盤とCreate Display Link。真空・極低温・磁石・点火・出力・緊急ダンプを実操作 |

| 蒸気系 | ドラム→独立配管3本→高圧段3組→低圧段3組→30 °C復水→受槽→共通昇圧ポンプ→ドラム |
| 回転系 | 3列共通軸、16ローター発電機、核融合炉用電動発電機、大型フライホイール |

外付けラジエーター／復水器の配管は使っていない。低圧タービンが30 °Cの液体水を排出し、ドラム内でブランケットから戻る高温水と混ざる構成である。

## 試験手順

1. 未リンクの制御盤が操作を拒否することを確認し、Display Linkで炉へ接続する。
2. 真空排気、液体He冷却、超電導磁石充電、プラズマ点火を順に行う。
3. 80パーセント（400 MW）へ上げ、蒸気を3列の高圧・低圧タービンへ送る。
4. 軸を同期し、炉用電動発電機を有効化して始動電源を切り離す。
5. 20,000 tick保持し、温度・圧力・流量・質量・熱収支を連続監視する。
6. プラズマ停止と再点火、蒸気喪失と復旧、緊急ダンプを順に行う。
7. ダンプ完了まで温度・圧力・回転数を監視し、破損や爆発がないことを確認する。

## 報告された9件の原因と修正

| # | 不具合 | 原因 | 修正と回帰確認 |
| ---: | --- | --- | --- |
| 1 | 40 MWを給電できない | 400 V負荷の抵抗が低すぎ、電線・発電機の内部抵抗と許容電流に合わなかった | 20 kV・120 MWの軸直結電動発電機と大型フライホイールを追加。定常時42.105 MW軸入力→40 MW給電、始動電源切離し後も運転継続を確認 |
| 2 | 高圧段が8.27 bar以下で固着し`wet`になる | 背圧以下の乾燥蒸気を品質0として扱い、圧力回復後も流れを作れなかった | 背圧以下の乾燥蒸気を低圧側へ圧力通過させ、表示を`pressure`に変更。3列のダンプ後再始動を確認 |
| 3 | 発電機接続状態では始動できない | 始動時の仕事見積りが64 mBだけで、実際の最大蒸気流を評価していなかった | 過負荷中も蒸気膨張を進め、最大流量から始動能力を見積る。回転網再構築時に容量を再登録し、接続状態で256 RPMへ始動する試験を追加 |
| 4 | 同一ローターの2面に触れる配管で蒸気が消える | 面ごとのハンドラを別受入先として予約し、同じ内部タンクへ二重投入していた | 容器ごとの予約量を共有し、SIMULATEとEXECUTEの差を返送。見えているCreate配管面だけを経路として扱い、二面接続でも全質量を保存 |
| 5 | 400 MW中も冷却水エラー表示 | tick末に空になる正常な入口バッファを異常判定していた | 燃焼状態を優先し、流量判定に20 tickの猶予を追加。燃焼中`burning`、実喪失時だけ警報になる回帰試験を追加 |
| 6 | 新設炉が最初から240 °Cで無から加熱する | ブランケット初期値と読込時既定値が240 °Cだった | 外気温から初期化。未点火時に冷却水へ正味熱が加わらない試験を追加 |
| 7 | タービン1組の流量が頭打ち | 低圧入口が空のtickだけ段間蒸気を送っていた | 同圧時も蒸気小包全体を低圧段へ渡す。実プラントでは3列を独立配管として均等運転 |
| 8 | 大タンクに触れた配管走査が重い | 蒸気を出さないタンクまで毎tick全面走査していた | 実際に水を沸かすCreateボイラーだけを対象にし、プラント容器を除外。結果を20 tickと配管トポロジー単位でキャッシュ |
| 9 | 復水管を合流すると2列が停止 | 複数の加圧流が同じ合流点で方向を奪い合った | 各列を受槽まで独立排水し、受槽から単一の昇圧ポンプでドラムへ送る。全ローターから復水を回収する試験を追加 |

## 追加で直した箇所

- 大型フライホイールの伝達上限を約10 MW相当へ上げ、駆動中も蓄勢出力を公開するようにした。
- 回転網のクラッチ切替後、応力容量と負荷を即時更新するようにした。
- SteamMain、ボイラー蒸気出口、タービン設備の接続判定を、単純な隣接ではなく実際のCreate配管面へ統一した。
- 耐圧タンクをCreateボイラー判定から除外し、50 barの液相・気相保持を個別試験した。
- 炉の短い電源切替では点火熱だけを20 tick保持し、その他の安全インターロックは即時動作するようにした。

## 実プレイ上の制約

- D₂、T₂、液体Heの製造ラインはまだないため、この試験では開始時にタンクへ投入した。燃料製造は別機能の範囲である。
- 一次冷却・給水・真空ポンプはクリエイティブモーターで回した。炉の磁石と加熱40 MWだけは、実際の蒸気タービン軸・電動発電機・フライホイールで自己給電した。
- 16ローター発電機は2.359 MWの確認負荷である。残る73.82 MWの軸余力をすべて電力へ変換するには、発電機列を追加する必要がある。
- 長期消耗はブランケット寿命で進むが、今回の20,000 tickを超える交換・遠隔保守までは試験していない。
- 測定値はゲームモデルの値であり、実在炉の安全評価や工学設計には使用できない。

## 再実行

```bash
JAVA_HOME=/workspace/.createplant-jdk21 \
PATH=/workspace/.createplant-jdk21/bin:$PATH \
bash ./gradlew --no-daemon runFusionPlantGameTestServer
```

保持時間を変える場合は`-Dcreateplant.fusionPlantHold=<tick>`を付ける。短い開発試験では`-Dcreateplant.fusionPlantFastStart=true`を併用できる。試験は専用の`@ExplicitGameTest`なので、通常の`runGameTestServer`とは別に実行する。
