## 実装内容

### 1. Ponder字幕の折り返し（`client/JapaneseLineBreak.java`、`mixin/PonderTextWrapMixin.java`）

- 原因：
  - Minecraft の行分割（`StringSplitter`）は、半角スペースだけを改行位置の候補にする。候補がない行は、幅いっぱいの文字で切る。
  - 日本語の字幕で半角スペースがあるのは「160 Ω」「2 mB」のような数値と単位の間だけなので、そこで改行され、行の後ろ半分が空いていた。
- 対策：このMODのPonderの日本語の字幕だけ、行分割を日本語向けの処理に替える。
  - 改行してよい位置：日本語の文字（ひらがな・カタカナ・漢字・全角記号）どうしの間。
  - 改行しない位置：
    - 英数字の続き（「160 Ω」「2 mB」「Create」など）の中。
    - 閉じ括弧・句読点・小さい仮名・長音（「。」「、」「）」「ッ」「ー」など）の前（行頭禁則）。
    - 開き括弧（「（」「「」など）の後（行末禁則）。
  - 1行より長い英数字の続きだけは、幅いっぱいで切る。
- Mixin：Ponder の `TextWindowElement.render` の中の2か所だけを置き換える。
  - `StringSplitter.splitLines`：行の一覧。
  - `Font.wordWrapHeight`：枠の高さ（行数×行の高さ）。
  - 対象は、場面の名前空間がこのMOD（`create_heavy_indusstry`）で、文字列に日本語を含むときだけ。英語や他MOD（Createを含む）のPonderは、元の処理のまま。
- 毎フレーム呼ばれるので、直前の結果（文字列と幅）を1つだけ保持して使い回す。
- 最初は、日本語の字幕の半角スペースを改行しない空白（U+00A0）に置き換える方法を試した。行は埋まるようになったが、「2 / mB」のように数値と単位の間で文字単位に切れることが残ったため、取りやめた。

### 4. 負荷の計測（`client/LoadClientCheck.java`）

- 計測の方法：
  - クライアント検査の仕組み（`ClientQualityCheck`）に、計測用の検査を追加した。`-Dcreateplant.clientQualityCheck=true -Dcreateplant.loadClientCheck=true` で動く。
  - 平らなワールドの統合サーバーで、状況ごとに設備を置き、200 tick 待ってから300 tick の間、サーバーの1tickあたりの平均時間（`getAverageTickTimeNanos`、直近100 tick）を100 tickごとに読む。終わったら片付けて次へ進む。
  - 同時に Java Flight Recorder（JFR）でサーバースレッドの実行を記録し、各処理が占めた割合を数えた。
- 状況と結果（1回目、全状況。数値は100 tickごとの平均 ms）：

| 状況 | 1tickあたりの時間（3窓） | 平均 | 空のワールドとの差 | JFR：Create-Plantのコードの割合 |
| --- | --- | --- | --- | --- |
| 空のワールド | 8.58・7.27・6.55 | 7.47 | 0 | 0% |
| 開放円筒タンク64基（直径8、水入り、砂浜） | 7.92・7.51・8.06 | 7.83 | ＋0.36 | 2.5% |
| Createの配管30本×16列、ポンプで90 °Cの水を送る | 7.82・7.06・7.36 | 7.42 | −0.05 | 3.2% |
| 気体パイプ120本×16列（両端にタンク） | 8.99・7.83・8.06 | 8.29 | ＋0.82 | 0.7% |
| 電解槽の列128（鉢2・極板8・水入り、電力なし） | 7.01・6.31・7.68 | 7.00 | −0.47 | 8.4% |
| Createのタンク256基（90 °Cの水）とブタ200匹 | 8.37・8.96・8.88 | 8.74 | ＋1.27 | 2.6% |

- 分かったこと：
  - 空のワールドでも窓ごとに約2 ms揺れる（xvfbのソフトウェア描画と同じCPUで動くため）。1tickあたりの時間の差は、どの状況も揺れの範囲内だった。
  - 気体パイプの差（＋0.8 ms）は、Create-Plantのコードではなく、継承元のCreateの配管の処理（1,920本）によるものだった。
  - 電解槽だけ、Create-Plantのコードの割合が大きかった。中身は：
    - 列の検索（`BasinClusterManager.findCluster`）が、1tickに鉢の処理（列の各鉢）と、CEEの回路処理の2回（`preTick`・`postTick`）で、別々に行われていた。
    - 電力がなく反応できないときも、毎tick 鉢の溶液を全部数えていた。
- 改善（`basin/BasinElectrolysis.java`）：
  - 見つけた列を、その鉢の状態に「見つけたtick」と一緒に保持し、同じtickの中では使い回す。列の鉢が1つでも無くなっていれば、その場で探し直す（壊した同じtickに気体を出さない既存のテストを満たす）。列が無い鉢は保持せず、毎回探す。
  - CEEの`preTick`・`postTick`はサーバースレッドで呼ばれる（CEEは回路を解く計算だけを別スレッドで行う）ことを、CEEのクラスとJFRの記録で確かめた。
  - 電力がなく1枚分の電力量もたまっていないときは、溶液を数えずに止める。ゴーグルは「電力なし」を「溶液なし」より先に表示するので、表示は変わらない。電力の有無が変わったときだけ、表示を同期する。
- 改善の前後の比較（同じ状況「電解槽の列128」と空のワールドを交互に3回ずつ。JFRの記録間隔1 ms。数値は、サーバースレッドが動いていた時間のうちの割合）：

| | 変更前（3回） | 変更後（3回） |
| --- | --- | --- |
| Create-Plantのコード全体 | 18.9%・19.5%・19.1% | 14.6%・17.2%・16.8% |
| 列の検索 `findCluster` | 8.5%・7.7%・9.8% | 4.3%・5.2%・5.6% |
| 溶液の集計 `solutionIn` | 2.0%・2.9%・1.4% | 0% |

  - 1tickあたりの時間（ms）は、変更前 9.05・7.79・7.86、変更後 8.79・8.66・8.48 で、揺れが大きく差は判定できない。改善は処理の割合で確かめたもので、1tickあたりの時間の短縮は主張しない。

## 未検証・制約

- 負荷の計測は、xvfb上のソフトウェア描画と同じCPUで統合サーバーを動かしたもの。空のワールドでも1tickあたりの時間が窓ごとに約2 ms揺れるため、1 ms未満の差は判定できない。専用サーバー・実機での計測はしていない。
- 動力付きの電解槽（CEEの回路から実際に電力を受けている状態）、ポンプで流れるガス、ボイラーの蒸気、RBMKなどは計測していない。
- 日本語の折り返しは、目で見て確かめたのは「塩・塩素・苛性ソーダ」「鉢の電解槽」の2つの場面。全93場面の題名の一致は検査で確かめた。

## 次回の注意

- 日本語の字幕は、数値と単位の間に半角スペースを入れたままでよい（折り返しで分かれない）。
- 撹拌反応槽にレシピを足すときは、材料の組が既存と重ならないようにする。硝酸の吸収（二酸化窒素＋水）は、水を使う反応（硫酸・塩酸・エチレングリコール）と同じ反応槽に入れない。
- 負荷を測るときは `-Dcreateplant.clientQualityCheck=true -Dcreateplant.loadClientCheck=true -Dcreateplant.loadScenarios=0,4` のように状況を選べる。結果はゲームのフォルダの `load-check.txt`。
