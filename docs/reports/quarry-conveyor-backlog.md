# クァーリーの搬送滞留とクライアント負荷

2026-11-17（JST）。実装コミットは `145494f13c84ec66a9c073675ed0ca9b2c4643a6`。

## 調査

稼働クライアントの JAR で `QuarryConveyor` の搬送・NBT と `QuarryRenderer` の全件描画を確認した。詰まった橋に荷物を追加し続けるため、ヘッドの箱が満杯になる前に橋上の荷物が増え続けた。荷物の移動や装置の状態変化のたびに全件がクライアントへ同期され、停止中でも毎フレーム描画された。

30 秒の JFR では描画スレッドの 1,227 サンプル中、Quarry の描画が 819 件あり、うち 511 件のスタックに搬送品の `ItemRenderer.renderStatic` が含まれていた。サンプルの割合から FPS の改善幅は算出していない。

## 実装

- `QuarryConveyor` はシュート・橋の先頭と末尾を参照して搬送する。橋には `ceil(移動ステップ数 / 8)` 便まで新規配置する。幅64では橋33便とシュート4便。満杯はヘッドの箱まで伝わり、採掘は既存の満杯判定で止まる。既存の滞留品は橋の先頭から部分搬出できる。
- ワールドへの保存は全件を保持する。旧保存の `Now × 4` を開始時刻または `LastLaunch` が上回る場合だけ、保存時計をその上限まで進め、次の保存単位にそろえる。最後の荷物を搬出したときも保存対象にする。
- `QuarryDriveBlockEntity` の同期はゴーグル用の総数と、先頭・移動中を中心とした最大40便の表示データを送る。旧サーバーの全件パケットでもクライアントの荷物デコードは最大40便。`QuarryRenderer` は出口やシュートの上端で重なった荷をそれぞれ1モデルで描画する。Ponder の開始時刻は保存時計と同じ単位で計算する。

## 検証

Java 21、Minecraft 1.21.1、NeoForge 21.1.219、Create 6.0.10。Gradle `build` と、`createplant.gameTestClasses=QuarryGameTests,QuarrySpeedGameTests` に絞った専用 GameTest サーバーの12件が成功した。

| ケース | 結果 |
| --- | --- |
| 幅64、搬出を2,000内部ステップ拒否 | 橋33便、シュート4便で頭打ちになり、ヘッドの箱が満杯。生成数と保持数が一致 |
| 11,683便と先行した時計を持つ旧形式の保存 | 全便の順序・時刻・アイテムのコンポーネントを保存し、部分搬出で計186,928個を順番どおりに搬出 |
| 同じ11,683便の同期 | 同期 NBT は1,349,787バイトから3,537バイト。新パケットは表示27便と総数11,683便。旧パケットを新クライアントで読み込む場合は表示40便 |
| Create ベルトでの実搬出と既存の速度試験 | 鉱石24個を全数回収。64 RPMで土45ブロックを83ワールドtickで採掘 |

同期量は圧縮前の BlockEntity NBT の比較。Ponder 言語・チュートリアルの静的検査も成功。素材分類の検査 `validate_visual_identity.py` は変更前の `main` でも失敗している。 [変更前の CI](https://github.com/Chemi-Create-Team/Create-Plant/actions/runs/44038437140)

稼働環境の FPS とフレーム時間は未計測。配備時にはサーバーとクライアントの JAR をそろえ、同じ視点と設定で JFR を再採取する。
